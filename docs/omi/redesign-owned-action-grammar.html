OMI · design reference · not built yet

Owned, redesigned around one clear path.

Same features, same house style — reorganised so a page answers “what do I do first?” on its own. Three moves: one primary path per surface, everything else demoted to read-outs and secondary links, and a quiet function pip so you always know what kind of work you’re looking at. Built for the agent to replicate in dev/platform/frontend.

Four visual jobs, applied the same way on every page. The rule that fixes the overwhelm: if everything is a button, nothing is primary.

These 7 hues are the only place function colour appears. Buttons stay accent-yellow; surfaces stay white; deltas keep the sanctioned green/red. The pip is a wayfinding token, not a theme — it’s the one considered step beyond the two-tone palette, kept muted so it never competes with the accent.

Notes for the build

Rules to enforce everywhere
  • One .btn-primary per surface — the primary path.
  • Optional actions → .tlink / ghost, never filled.
  • Read-outs → the .readout card w/ ⓘ, never clickable-as-a-step.
  • Reuse OMI’s existing INFO_TABS flag to decide read-out vs step.
Reuse, don’t reinvent
  • All tokens/primitives already exist in src/index.css.
  • Add only: --fn-* pip hues + .readout + .tlink.
  • The 5-step rail is the existing ProcessRail/Stepper.
  • Ship as the Owned Overview first; then apply to Paid & Shared.

Mockup renders with a system-font fallback — the real app uses Brockmann. Colours, borders, radii and shadows are OMI’s own tokens, unchanged.
